# SDO 游戏更新与补丁缓存

国服更新接口会分别为 `ffxiv` 和各资料片仓库返回补丁列表。一个补丁条目由完整 URL、目标版本、长度和可选的分块 SHA1 共同标识；不能只用 URL 的最后一段文件名和版本号判断它是哪一个补丁。

## 为什么完整 URL 是补丁身份的一部分

不同仓库可能返回相同 basename 和版本号，例如：

```text
.../ffxiv/.../D2026.07.16.0001.0000.patch
.../ex5/.../D2026.07.16.0001.0000.patch
```

如果缓存名只有 `basename + version`，后下载的文件会覆盖先下载的文件。安装器随后可能把错误仓库的 ZiPatch 应用到当前仓库，并继续推进 `.ver`，最终表现为版本检查已是最新、游戏启动却报 `1012`。

当前缓存名包含完整 URL 的 SHA1：

```text
<sha1(url)>-<basename>.<version>
```

URL 哈希只用于隔离缓存身份，不替代补丁内容校验。旧的 `basename + version` 缓存文件会保留，但新代码不会再复用它们。

## 下载与安装的校验边界

下载器和安装器都会验证缓存文件：

- 文件长度必须与补丁列表一致，包括没有分块哈希的 boot 补丁。
- `hash_type=sha1` 时，每个块都必须匹配服务端给出的 SHA1。
- 安装前会再次执行相同校验，防止下载完成后文件被替换或缓存身份混淆。
- 校验失败时不得应用 ZiPatch，也不得更新仓库的 `.ver` 文件。

因此 `.ver` 表示已经成功应用的版本，而不是已经下载或尝试安装的版本。

## `1012` 的恢复原则

如果旧缓存碰撞已经让 `.ver` 超前，应先备份版本文件，再只回退确认受影响的仓库版本。随后重新请求缺失补丁，让更新器使用唯一缓存键重新下载、校验和应用。不要直接删除整个游戏目录，也不要把所有仓库统一回退到同一版本。

恢复完成后至少验证两件事：

1. 再次执行版本检查，服务端不再返回缺失补丁。
2. 实际启动游戏并进入大厅或角色界面，确认本地数据与版本报告一致。
