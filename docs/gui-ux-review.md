# GUI UI/UX 审查与设计建议

## 结论与审查边界

当前界面已经有克制的黑白灰配色、统一中文字体、基础组件和部分异步状态处理，但整体仍偏“配置与调试工具”，尚未形成以“顺利进入游戏”为中心的产品体验。首要工作不是增加装饰或更换颜色，而是重做任务层级、状态反馈和恢复路径。

本审查基于当前工作区（包括未提交改动）的全部 GUI 页面、共享状态、入口、日志及相关启动 API，并核查 Cargo.lock 对应的 Blitz 本地源码。没有完成原生窗口的截图和逐项人工交互验证；首屏拥挤程度、实际裁剪、字体绘制和 GPU 性能属于待实机验证项，不将源码推断写成实测结果。未改动产品实现。

范围：首次配置、日常启动、账号管理、扫码/推送/密码登录、更新、Wine、Dalamud、设置保存、错误恢复、键盘操作、视觉规范和动效。Windows/macOS 原生效果不能由 Linux 或浏览器预览替代验收。

## 设计方向

- **产品**：让国服 FFXIV 玩家可靠、少操作地完成登录、更新和进入游戏。
- **性格**：安静、可靠、直接。
- **世界**：艾欧泽亚的入口，而不是运维监控台；保留现有 zinc 亮色和黑色主操作。
- **重点**：账号与大区组成清楚的启动上下文；准备、更新和启动过程是唯一需要动态强调的区域。
- **识别细节**：用一致的“就绪标记 + 具体阶段”表达距离进入游戏还有什么；不依赖装饰性游戏背景、发光、渐变或动态壁纸建立识别度。

## 一、必须优先解决的任务与状态问题

### 1. 首次进入页面不等于首次配置引导【高】

依据：`packages/eorzea-app/src/ui/mod.rs:113`，无账号或无游戏路径一律进入账号页；`login.rs:72` 的空状态只提示添加账号。

- 已有账号但没配置路径，仍被送到账号管理；用户不知道下一步在哪里。
- 添加账号后停在账号页，没有接续配置或进入游戏的动作。
- 游戏目录缺失时，主页与按钮反馈都要求用户自行寻找设置。

建议：按缺失条件展示准备清单，而不是强制线性向导：“选择游戏目录”“添加账号”“检查运行环境”。每项直接完成对应操作，保留跳过/稍后配置；全部具备后只显示“进入游戏页”。已有目录或账号应自动识别，不让用户重复操作。尚不支持全新游戏下载时明确说“选择已有游戏”，不要暗示能够安装完整客户端。

### 2. 主页的视觉顺序与任务重要性相反【高】

依据：`home.rs:491–689`，依次为启动设置、游戏位置/版本、Dalamud/Wine、更新、启动、200px 日志；默认窗口为 720×860（`main.rs:17`）。

建议：主页上部只回答“用谁、去哪个大区、能否启动”，主操作必须在默认窗口首屏可见，且不随日志增长移动。四块状态卡合并为紧凑“运行环境”摘要，路径和完整版本按需展开；日志默认收起。不是把现有卡片全部重新涂色。

### 3. 更新任务不是应用级任务【高】

依据：`home.rs:46–47, 95, 130`，更新状态和补丁列表属于主页局部 signal，使用页面 scope 的 `spawn`；与启动采用全局 `launching` 和 `spawn_forever` 不同。

切页会卸载主页，存在取消更新任务、丢失任务呈现的风险；尤其安装过程不能把“页面生命周期”当作事务边界。任务已产生的磁盘副作用是否还能继续，需要结合底层应用函数验证，不能承诺切页即安全取消。

建议：检查/下载/校验/安装放入应用级任务服务，页面只是订阅视图。切页后持续运行并显示同一任务；安装期禁止不安全取消，退出时按阶段解释后果。只有底层实现安全暂停/取消后才能提供对应按钮。

### 4. 更新与启动缺少互斥【高】

依据：`home.rs:85–94, 157–186, 620–668`，检查/更新只检查更新状态，启动只检查 launching；启动按钮也没有真实 `disabled`。

建议：在任务层统一保护游戏目录，而不只是按钮改灰。下载期间是否可启动需要明确策略；校验/写入游戏文件期间必须阻止启动。启动期间不能开始修改同一游戏目录的任务，不能切换当前任务使用的目录。界面显示原因，例如“正在安装补丁，完成后可启动”。

### 5. 所有消息共用一条可覆盖的字符串【高】

依据：`mod.rs:57–58, 242–246`；登录、区域列表、配置保存、Dalamud 下载、游戏启动都写 `state.status`。

结果：关键错误与普通成功提示相互覆盖；错误与次要说明都用灰色；长错误让状态栏增高；用户看到“失败”却没有直接操作。

建议拆为：

- **持续任务状态**：放在主操作区域，阶段、进度和取消能力清晰可见。
- **阻断错误**：留在相关区域直到解决，包含简短原因与恢复按钮。
- **轻量成功反馈**：局部“已保存”等，不抢占任务状态，不移动布局。
- **技术详情**：折叠查看、复制诊断信息；日志不能成为理解状态的前提。

### 6. 自动登录失败没有重新认证闭环【高】

依据：`home.rs:267–280` 提示“请到登录页”；实际导航名称是“账号管理”；账号卡没有“重新登录”（`login.rs:108–149`）。

建议：自动登录失效时原位展示“账号需要重新登录 → 重新登录”并打开绑定该账号的登录弹窗；成功后恢复待执行操作，或给出明确“继续启动”。网络失败与凭据失效应分开，前者提供重试，不能一律要求重新认证。不要让用户用“重新添加”猜测如何修复既有账号。

### 7. 保存失败后，账号仍可能表现成添加成功【高】

依据：`mod.rs:97–105`，保存结果无论成功失败都更新内存账号、缓存 token、关闭添加弹窗。

建议：区分“本次已登录”和“已保存到本机”。失败时保留可恢复状态并明确提供重试；若允许临时使用，必须标注“仅本次使用，退出后不会保留”，不能只在灰色状态栏顺带说明。自动登录 key 轮换后的持久化失败（`home.rs:259` 忽略保存结果）也应单独处理，避免下次启动凭据失效却无解释。

### 8. 设置草稿离开页面即丢失【高】

依据：`settings.rs:27–76` 草稿在页面 scope 初始化；`NavButton` 直接切页（`mod.rs:281`）。

建议：保留应用级草稿，或切页/关窗时提示“保存 / 放弃 / 继续编辑”。保存栏显示“有未保存的更改”；“恢复”改为“放弃更改”，避免误解成恢复出厂设置。已有固定保存栏和 dirty 判断应保留。

## 二、各页面的交互与信息设计

### 共享导航与选择控件

1. **下拉展开导致主布局跳动**：`mod.rs:298–305, 386–389` 为兼容层叠问题使用文档流内展开；账号或大区一展开就把下面的状态、主操作顶走。当前规避有技术理由，但不应视为最终产品交互。优先做原生弹层探针；仍不可靠时，采用位置稳定的选择对话框/独立选择面板，不为了模仿网页下拉反复依赖失效的 z-index。少量选项可用明确的单选组。
2. **下拉只有 Escape，没有完整选择交互**：选项使用 aria-pressed 的按钮，没有方向键导航、打开后的焦点定位和选中后焦点恢复。统一实现键盘模型与语义，不仅补 aria 属性；点击选项后保持主操作位置稳定。
3. **图标导航依赖悬停 title**：三个目的地可保留窄导航，但要验证原生 title 提示是否真的出现；若无可靠提示，使用简短常显文字或经过验证的提示组件。游戏使用房子图标语义偏“首页”，可以考虑与启动任务更贴近的单一线条图标，不必为此扩大侧栏。

### 游戏页

1. **启动就绪条件不可见**：没有账号、目录无效、初始化未完成时仍像可正常启动，点击后才报错。用页面内缺失条件和对应 CTA 引导；有阻断条件时主操作直接变为“选择游戏目录”或“登录账号”，不能只禁用而不解释。
2. **缺少更新大小与阶段信息**：只报补丁个数；下载 100% 后突然进入“安装中”。检查完成展示总下载量及缓存复用情况；利用已有安装进度回调替代 `install_verified(..., |_| {})`（`home.rs:142`）。明确下载、校验、安装是不同阶段，100% 只代表当前阶段。速度/剩余时间仅在可信时提供。
3. **失败后重试路径不完整**：更新失败状态不再显示“更新游戏”按钮（`home.rs:624`），用户必须猜测重新检查。按失败阶段提供“重试下载”“重新检查”等；保留已完成的安全工作。
4. **区域列表失败仍显示加载中**：placeholder 只根据空列表判断（`home.rs:322`），获取失败仅写全局状态（`mod.rs:196`）。建立加载/成功/为空/失败四种状态，失败时提供原位重试；区域列表不可用不应阻碍账号操作。
5. **版本信息可能不刷新**：`use_memo` 仅依赖路径（`home.rs:77`），同一路径更新完成不会自动使本地版本重新读取。安装成功刷新版本和就绪状态；“发现了 exe”不能等同于“版本最新”。
6. **Wine 摘要不等于所选模式的实际结果**：主页调用 `detect(custom_path)`，并非完整按 startup_type 解析（`home.rs:425–440`）。卡片应显示实际采用/将采用的运行环境；自动模式缺少本地 Wine 时说明“首次启动将下载”，而非笼统报故障。不要在状态检查阶段意外触发下载。
7. **Dalamud 状态与本次开关分离**：卡片基于全局 enabled，本次开关另存，可能出现卡片“未启用”却勾选加载，或显示“启动时加载”但本次已关闭。将“默认设置”“本次覆盖”“安装兼容状态”明确区分，摘要以本次启动为准。
8. **Dalamud 首次准备隐藏在小状态栏**：大文件下载期间只看到“启动中”。准备阶段进入统一任务区。兼容失败提供“不加载插件启动”这一明确、单次的选择，不静默关闭，也不要求用户读长文案找开关。显式安装入口可放在插件设置，避免首次启动承担所有准备工作。
9. **日志默认展开占据主视图**：保留排障能力，但改为按需打开的独立日志面板，不能使用文档流内的折叠区域。打开、关闭和新增日志均不得改变主页其他区域的位置、尺寸及滚动位置，也不通过收窄主页给面板腾空间。建议采用覆盖式面板：位于页头与固定主操作区之间，自身滚动，保留关闭入口，不遮挡启动操作；窄窗口采用独立日志对话框。错误时只提示有详情，不自动打开或抢焦点。提供级别、复制脱敏信息、清晰的时间顺序；用户阅读历史时不要因新日志插入而打断位置。覆盖层的层叠、裁剪、命中与焦点需原生验证，不能因 Blitz 限制退回会推挤主页的内联展开方案。

### 账号管理

1. **卡片宽度随账号数量变化**：`flex: 1 1 240px` 让单账号撑满整行，多账号宽度重新分配。账号通常是重复结构，紧凑列表更适合快速比较：账号、默认大区、凭据状态、操作。卡片不必全部删除，但应有合理最大宽度。
2. **默认、当前选择、会话登录是三种状态**：当前默认用 disabled 按钮表示，难与不可操作区分；设默认不会同步当前选择。用“默认”静态标记，并明确“下次打开默认选择”；如果保留当前账号另选，视觉上分别表达，不隐式混淆。
3. **删除是每张卡上持续高亮的红色操作**：降级为次要操作；文案用“从本机移除”，确认时展示账号和“不会注销盛趣账号”。已有二次确认应保留；删除当前账号后选取合理回退或立即提供添加入口。
4. **凭据状态太技术化且无操作**：“本次会话”“自动登录凭据”可在详情解释；列表用“可尝试自动登录”“需要重新登录”，未验证的凭据不能显示为确定已登录。
5. **缺少登录完成后的下一步**：首次添加完成提供“前往游戏”；重复添加/重新登录已有账号时，应准确说“登录已更新”，而非一律“账号已添加”。

### 添加账号弹窗

已有的默认扫码、自动获取二维码、取消本地任务、密码不落盘、Escape 关闭、输入标签值得保留。

1. **等待状态不够细**：二维码状态仅 Idle/Loading/Waiting/Failed，扫码与手机确认未区分；推送没有可见倒计时。底层能提供状态时分别展示“等待扫码 / 请在手机确认 / 登录处理中”；不能伪造没有协议依据的状态。到期后用“二维码已过期 · 刷新”，而不是裸错误。
2. **加载态高度变化**：二维码出现前后和切换登录方式会改变内容高度。预留二维码区域，弹窗保持稳定宽度和合理最小高度，但不能为稳定而在小窗口强制溢出。
3. **缺少表单提交行为**：账号密码是普通输入和 `type=button`，没有 form/Enter 提交；密码不支持显示/隐藏。提供明确提交键、字段级错误；显示密码需有可访问名称，切换不丢失光标。账号/密码字段设置合理的自动完成语义。
4. **焦点管理只完成了一半**：有初始 focus，但没有显式焦点约束、背景不可交互和关闭后焦点恢复。`aria-modal` 本身不会实现这些行为；需在原生端验证并补齐。
5. **账号组选择未接入 GUI**：当前使用 `wait_for_scan(None)` / `wait_for_confirm(None)` 直接完成默认账号；核心已有 poll/finalize 和账号组能力。多账号组场景应在确认后增加选择步骤；单账号直接通过，不给所有人增加页面。
6. **Tab 名称重复冗长**：弹窗标题已有登录语境，标签可缩短为“扫码 / 推送 / 密码”，下方说明扫码和推送使用叨鱼；避免窄窗口中文被挤成多行。

### 设置页

1. **普通设置与排障参数同级**：默认仅展示游戏位置、运行环境选择、是否启用 Dalamud；将同步机制、Prefix、注入方式、通道、初始化延迟、插件禁用归入相应“高级/故障排查”。不把已有能力删除，而是渐进披露。
2. **Wine 模式缺少决策帮助**：“自动 / 托管 / 自定义 / 系统”只列名词。每项附一行结果说明，自动项标明实际优先级或将选择的工具；仅自定义时显示路径，提供文件选择和检测结果。
3. **“同步方式”看起来是滑块，实际是点击 div**：不支持 Tab、方向键、Space；这也不是连续量。使用有 radio 语义的三选一控件，不让用户误以为能拖动。当前“关”实际对应三种 flags 关闭/使用 Wine 默认，不能宣称关闭了所有现代同步后端；建议“Wine 默认 / esync / fsync”，并注明平台和构建能力限制。
4. **自制 switch 无键盘入口**：`SwitchRow` 是 role=switch 的 div，没有 tabindex 和键盘处理。优先使用 button/checkbox 构建，明确可访问名称、Space 切换与焦点态；视觉滑块不是交互语义。
5. **初始化延迟没有单位，非法值静默回退**：普通文本输入经过 parse 后默认化（`settings.rs:117, 181`）；输入 abc 可能被保存成默认值，dirty 判断也可能不反映输入。标注毫秒，限定非负整数与范围，非法时字段报错并阻止保存；空白默认语义与 0 的语义保持一致。
6. **路径校验覆盖不足**：目前仅检查 exe 存在；应区分空值、目录无效、选到了 game 子目录、不可写和 Wine 不支持的非 ASCII 路径。对能够明确识别的错误给“使用上一级目录”等安全修正建议，不悄悄改路径。必要的检查异步执行，避免每次输入扫描磁盘。
7. **固定 80px 标签列与长选项组**：宽度不足会挤压输入；Wine 选项行没有 wrap。约定最小窗口尺寸，小宽度下标签置顶、按钮换行。默认路径不能只依赖 placeholder；长路径提供查看/复制真实值的方法，不为省略牺牲可读性。

## 三、视觉与组件系统

### 应保留的基础

- zinc 黑白灰、无渐变无发光，符合工具型启动器，不需要另造品牌色。
- 72px 图标导航适合三目的地的小工具，不必扩大成管理后台侧栏。
- SVG 线条图标、中文字体栈、6–8px 控件圆角可继续使用。
- 设置固定保存栏、账号删除确认和异步登录已有正确方向。

### 需要打磨的地方

- **卡片套卡片、处处边框**：Section 和 StatusCard 使用同一种边框、底色和近似标题，导致所有信息同权。主任务一个明确分区，普通设置用留白和分隔线，摘要不再每项一个盒子。
- **页面标题不一致**：只有账号页有清晰 h2；游戏和设置缺少对应页标题。统一页面标题、短说明、页面级操作位置，减少“启动设置/游戏更新”等管理后台式标题。
- **缺少显式交互态**：组件代码没有统一 hover/pressed/focus-visible 规范；不等同于断言系统完全没有默认焦点态。需实际检查原生输入反馈，补齐可见状态，避免只靠 cursor 表示可点。
- **字号与控件高度零散**：10/11/12/13/14/15/16/18/20px，部分按钮仅靠 padding 决定高度。收敛为少数角色；主体正文 14px，说明 12–13px，页标题 22–24px，主要按钮统一 40px，游戏主操作 44–48px。
- **提示符仍混用字形**：已有 SVG，但状态中仍用 ✓/✗/⚠。统一状态图标或点标记配文本，避免再依赖字体是否覆盖符号。
- **成功/警告小字对比度不足**：白底 #16a34a 和 #d97706 的对比度约 3.3:1、3.2:1，不满足普通小字号 4.5:1 的目标；灰色 #71717a 白底约 4.8:1 已接近边界，落到浅灰背景还需复查。语义文字用更深颜色，不仅用颜色表达结果。
- **平台 badge 是视觉噪声**：当前平台已确定时，不必在主页 Wine 卡持续展示“Linux / macOS”。技术范围说明保留在帮助/设置即可；不要把 10px badge 当关键说明。
- **产品称谓统一**：窗口标题为“FFXIV 国服启动器”，crate/产品名是 Eorzea。建议窗口“Eorzea · FFXIV 国服启动器”，界面只使用一套称呼；不是重命名产品。

建议规范：4px 间距网格；页边距 24px，分组间距 24–32px，组内 8–12px；正文行高约 1.5；控件圆角 6px、主要面板 8px；图标 18px/统一线宽，导航可保留 22px。前景/背景使用现有 theme token，补上 hover、pressed、focus、disabled 与可访问语义色，而非在各页继续追加内联色值。

## 四、建议的信息架构与关键流程

### 游戏页：一个上下文，一个主操作

上部显示产品/页面名和总就绪状态；账号、大区可直接切换；中部是紧凑运行环境摘要；主操作区固定在视图下部、不参与内容滚动；日志默认关闭，按需覆盖展示，不参与主页布局。默认 720×860 不强制扩窗来掩盖层级问题，较小窗口按最小支持尺寸另做验收。

主操作依据状态变化，但不是一套伪装成状态机的按钮文案：

- 无目录 → “选择游戏目录”。
- 无账号/凭据已确认失效 → “添加账号 / 重新登录”。
- 可以启动，尚未检查版本 → “启动游戏”，摘要明确“版本未检查”；是否自动检查需产品决定，不能谎称最新。
- 已发现更新 → “更新游戏 · 下载量”；保留次要检查入口，更新后由用户选择是否自动启动。
- 正在下载/校验/安装 → 显示同一任务的真实阶段，阻止不安全冲突。
- 正在启动 → 同一区域显示“准备插件 / 验证账号 / 启动进程”。
- 创建进程成功 → “已启动”；这不代表游戏已经进入可交互画面。是否检测游戏退出或单实例属于另需实现的能力。

### 失败是流程分支，不是死胡同

- 目录无效 → 选择目录，并即时校验。
- 区域列表网络失败 → 原位重试，不让“加载中”无限持续。
- 凭据失效 → 重新认证 → 回到待执行启动。
- Dalamud 不兼容 → 查看原因 / 本次不加载插件启动，不静默降级。
- 更新失败 → 保留缓存和任务上下文 → 重试失败阶段。
- 保存失败 → 保留草稿或临时登录状态 → 重试保存。

## 五、Blitz 动画支持与建议

### 能力结论

**当前版本有 CSS animation/transition 的实现基础，但不是完整浏览器兼容承诺。** 不需要为几个轻量动效立即换渲染器，也不能直接把网页动画方案搬过来。

锁定依赖：dioxus-native 0.7.10、blitz-dom 0.2.4、blitz-paint 0.2.1、blitz-shell 0.2.3。

本地依赖源码证据（位于 Cargo registry 对应包目录）：

- `blitz-dom/src/stylo.rs:74–145`：推进 animations/transitions、清理完成状态并计算是否还需 tick。
- `blitz-shell/src/window.rs:219–228`：以动画时间 resolve，活动动画继续 request_redraw。
- `blitz-paint/src/render.rs:168–229`：有 opacity 绘制路径，但透明度层存在裁剪等限制。
- `blitz-paint/src/render.rs:303–306`：支持部分二维 transform，仍明确标注变换后的命中测试和嵌套 transform TODO。

这些证据证明不是“完全不支持”，不证明任意属性、伪类、嵌套组合或帧率都可靠。浏览器端拥有自己的 CSS 能力，不代表原生端；浏览器 CSS 合成动画的性能经验也不能直接套到 Blitz 的 resolve/paint 流程。

### 动效取舍

- **优先验证并采用**：按钮/选项背景和边框颜色 100–140ms；状态切换的短透明度变化 120–160ms（避开复杂层叠/溢出内容）；没有进度数字的真实等待过程使用简单指示器。
- **有条件采用**：弹窗 140–180ms 淡入；开关滑块约 120ms 的短位移。位移会改变可点目标时，必须验证命中与嵌套限制，不能以“视觉正常”通过验收；如果不可靠，使用瞬时位置切换加颜色反馈。
- **暂不作为设计依赖**：弹出菜单浮层、页面整体滑入、嵌套 transform、可交互区域缩放、复杂透明层和 3D 动效。
- **明确避免**：无意义呼吸/闪烁、卡片 hover 放大、transition: all、长时间入场、自动轮播、动画移动启动按钮。二维码不做持续动画，不以虚假进度表示未知等待。
- **页面切换默认即时**：启动器要快，不必所有切页都淡出再淡入；退出动画需要保留组件到结束，不能让动画状态机拖延关闭/取消。
- **降低动态效果**：检测 `prefers-reduced-motion` 的原生适配是否真正生效；未验证前提供应用级关闭选项或保守默认，不能只写媒体查询就认为已完成。

建议先做一个无账号、无网络请求的原生动效探针：颜色 transition、opacity、二维位移、焦点与点击命中、动画结束后是否停止重绘；测试原生完整重启，而不只看热更新。动效必须能关闭，关闭后信息与操作完全等价。

## 六、实施优先级与验收

### 先保证可信与可恢复

应用级任务和目录互斥；更新切页/退出策略；持久化失败；认证恢复；草稿保护；区域失败重试；原生渲染细线与文字问题。现有细线问题尚无确认根因，不能靠改间距掩盖。

### 再重做主路径

准备清单、游戏页主次层级、统一任务区、收起技术详情、账号重新登录、设置渐进披露。保留当前功能与默认风格，不一次引入背景图、主题切换和庞大导航。

### 最后打磨反馈

统一组件高度/间距/语义色/焦点；原生兼容下拉；登录弹窗稳定布局；经过探针验证的少量动效。

产品级验收至少覆盖：

- 新用户不看文档即可选中已有游戏、添加账号并明确知道下一步；中途返回不重复配置。
- 默认窗口首屏能看到账号、大区、总状态和主操作，不需要滚动寻找启动按钮。
- 日志打开、关闭及持续新增内容时，主页布局与滚动位置不变；面板独立滚动，不挤压主页，也不自动弹出抢焦点。
- 更新时切换任意页面，任务状态、进度和游戏目录保持一致；不能同时启动和安装同一游戏。
- 每个阻断错误都有对应恢复动作，不要求去日志里找解决方法。
- 自动登录网络失败可重试，凭据失效可原位重新登录。
- 设置切页/退出不静默丢失；非法数字不可被无声替换；磁盘保存失败不会显示成已持久化。
- Tab 可达所有操作；Space/Enter 可用；下拉支持方向键和 Escape；弹窗焦点不逃到背景，关闭后恢复。
- 键盘 focus 与选中态区分；状态不只靠颜色；文本达到对比度目标。
- 长路径、长账号、多账号、错误长文本、系统 125%/150%/200% 缩放下无重叠；约定最小窗口尺寸。
- Linux/Windows/macOS 分别验证真实可用配置，不以隐藏控件代替能力规则；浏览器仅用于布局辅助。
- 无任务、无动效时不因动画持续重绘；日志更新不导致整页明显卡顿；动效关闭时功能等价。

审查方法参考 unslop（Damir Sokolovsky / @heydamir，CC BY 4.0）；以上结论和设计建议针对本项目实现。
